# 아군 유닛 Effects 조합 가이드

> `AllyUnitDefinition.effects`(리스트)에 `AllyUnitEffectBase` 파생 SO를 몇 개 얹느냐로 신규
> 아군 유닛/오퍼레이터를 만드는 가이드. 여기 나열된 조각들은 전부 이미 구현되어 있으므로,
> **새 C# 코드 없이 SO 조합 + 레시피 JSON만으로 신규 유닛을 만들 수 있다.** 이 문서가 그 조합
> 규칙과 실제 사용 가능한 부품 목록의 정본이다.

---

## 0. 왜 이 문서가 필요한가

Addressables 라이브 드랍(`ADDRESSABLES_LIVE_DROP.md`)은 **런타임 C# 코드를 재빌드 없이
배포할 수 없다.** 반대로 말하면, 이미 플레이어에 들어가 있는 Effect 클래스들을 조합해 새
`AllyUnitDefinition.asset`을 만드는 것은 **재빌드 없이 라이브 드랍 가능한 콘텐츠**다. 그래서
"지금 당장 안 쓰더라도" 여러 Effect를 미리 구현해두는 것 자체가 향후 콘텐츠 출시 속도를
좌우한다 — 이 문서는 지금까지 쌓인 부품과 그 조합 규칙을 정리한다.

---

## 1. 아키텍처 한 줄 요약

- `IAllyUnitEffect`(`Assets/Scripts/Effects/Unit/IAllyUnitEffect.cs`) 훅: `OnSpawn` / `OnTick` /
  `OnAttack` / `OnDeath`.
- `AllyUnitEffectBase`(SO, 상태 없음)가 편의 기본 구현. 구체 효과는 필요한 훅만 오버라이드.
- `AllyUnitInstance`(순수 C# 런타임)가 대상 선정·쿨다운을 **중앙에서** 관리하고, 정해진 시점에
  `Definition.effects`를 순회하며 각 효과의 훅을 호출한다 — 개별 효과는 "이 시점에 무엇을 할지"만
  안다("언제 부를지"는 모른다). 이 경계 덕분에 여러 효과를 갈등 없이 조합할 수 있다.
- `AllyUnitContext`(`Assets/Scripts/Runtime/AllyUnitContext.cs`)가 매 호출 넘겨주는 읽기 전용
  스냅샷: `self`, `activeEnemies`, `activeAllies`, `activeTowers`. 오라형 효과는 대부분 이 중
  하나를 매 틱 거리 필터링해서 쓴다.

---

## 2. 주 공격 Effect — 한 Definition에 하나만

이 네 가지는 전부 "명중 시 즉발 피해를 입힌다"는 동일한 역할을 하므로, 같은 Definition에 두 개
이상 얹으면 **주 타격이 중복 적용**된다. 반드시 하나만 고른다(서포트 전용 유닛은 0개 — 아래
§3 오라만으로 구성해도 된다). 네 Effect는 모두 `IAllyUnitPrimaryAttackEffect` 표식 계약을
구현하며, `AllyUnitAssetValidator`가 이 계약의 구현 수를 세어 2개 이상인 Definition을 오류로
차단한다. 구체 클래스 이름 목록이 아니라 역할 계약을 검사하므로 후속 주 공격도 같은 표식만
붙이면 자동으로 배타성 검증에 포함된다.

| 효과 | 파일 | 특징 | 잘 맞는 컨셉 |
|---|---|---|---|
| `BasicAttackEffect` | `Effects/Unit/Concrete/BasicAttackEffect.cs` | 최근접 1체에게 즉발 피해. `attackRange > ContactRange`(원거리)일 때만 `FakeProjectile` 연출 | 표준 근접/원거리 딜러 |
| `PierceAttackEffect` | `Effects/Unit/Concrete/PierceAttackEffect.cs` | 타겟 방향 부채꼴(`beamHalfAngleDegrees`) 내 사거리 안 모든 적을 동시 타격, `LaserBeamView` 연출 | 일렬로 늘어선 적 관통 저격수 |
| `SplashAttackEffect` | `Effects/Unit/Concrete/SplashAttackEffect.cs` | 주 타겟 + `splashRadius` 내 다른 적에게 `splashDamageMultiplier` 감쇠 피해, 착탄 연출 3종(`ParticleBurst`/`ShockwaveRing`/`ScorchDecal`) | 광역 폭발 근접/포격형 |
| `PoisonAttackEffect` | `Effects/Unit/Concrete/PoisonAttackEffect.cs` | 즉발 피해 + `poisonDuration` 동안 매초 `poisonDamagePerSecond` DoT(`EnemyInstance.ApplyPoison`, 재적중 시 갱신) | 지속 데미지형 암살자/독침 |

네 클래스 모두 각 SO 고유 필드가 아니라 **`ctx.self.Data.attackDamage`(Definition의 공용
스탯)** 를 기준 피해로 쓴다 — 같은 유닛 스탯 하나로 어떤 주 공격을 붙이든 밸런스 기준이
일관된다. 사거리/쿨다운도 마찬가지로 `Data.attackRange`/`Data.attackInterval`을
`AllyUnitInstance`가 공용으로 해석한다(§3 오라의 "attackRange를 오라 반경으로 재사용"과는
다른 용도이므로 혼동 주의).

Tower에 대응 클래스가 있는 것(Pierce/Splash/Poison)은 판정 로직을 `Assets/Scripts/Core/`의
공유 정적 유틸(`PierceAttackMath`/`SplashAttackMath`)로 추출해 Tower·Unit 양쪽이 같은 수학을
쓴다 — Tower 쪽 수치 조정이 Unit 쪽 판정 방식과 어긋날 일이 없다.

## 3. 오라(버프/디버프) Effect — 여러 개 조합 가능

주 공격과 달리 오라는 서로 배타적이지 않다. 한 유닛에 여러 오라를 동시에 얹을 수 있고(예:
이동/공속 버프 + 피해량 버프를 한 "지휘관" 유닛에 함께), 여러 유닛의 같은 축 버프는 곱연산으로
중첩된다.

공통 관례: **`attackRange` 필드를 "오라 반경"으로 재사용**한다. 순수 서포트 유닛(공격력 0)은
`attackDamage=0`으로 두고 `attackRange`만 오라 범위로 쓴다 — 예: `aurora-slow-drone`
(`attackDamage 0, attackRange 12`)이 `SlowAuraEffect` 하나만으로 구성된 실제 콘텐츠.

| 효과 | 파일 | 대상 | 축/효과 | 갱신 방식 |
|---|---|---|---|---|
| `TacticalRelayAuraEffect` | `Effects/Unit/Concrete/TacticalRelayAuraEffect.cs` | 근처 아군 유닛 | 이동속도·공속 배율 | 매 틱 거리 스캔, 짧은 지속시간 갱신 |
| `DamageBuffAuraEffect` | `Effects/Unit/Concrete/DamageBuffAuraEffect.cs` | 근처 아군 유닛 | 피해량 배율 | 위와 동일 |
| `TowerReinforcementAuraEffect` | `Effects/Unit/Concrete/TowerReinforcementAuraEffect.cs` | 근처 아군 타워 | 피해량·공속 배율 | 매 틱 거리 스캔 → `TowerInstance.ApplyTemporaryAura`(지속시간 기반) |
| `PitCrewRepairAuraEffect` | `Effects/Unit/Concrete/PitCrewRepairAuraEffect.cs` | 근처 아군 유닛 | 초당 회복(HoT), 정지 교전 중이면 배율 가산 | 매 틱, 풀피 대상은 스킵 |
| `SlowAuraEffect`(Unit) | `Effects/Unit/Concrete/SlowAuraEffect.cs` | 근처 적 | 이동속도 감속 | 매 틱 거리 스캔, 짧은 지속시간 갱신 |
| `VulnerableAuraEffect`(Unit) | `Effects/Unit/Concrete/VulnerableAuraEffect.cs` | 근처 적 | 받는 피해 배율 증가 | 위와 동일 |

`TacticalRelayAuraEffect`/`DamageBuffAuraEffect`는 둘 다 내부적으로
`AllyUnitInstance.ApplyStatMultipliers(source, effect, moveSpeedMultiplier,
attackSpeedMultiplier, damageMultiplier, duration)`를 호출한다 — 대상 인스턴스가
`RefreshableAuraBag<AllyUnitInstance, AllyUnitEffectBase, StatMultiplierSet>`(§5)에
(제공자, 효과) 키로 저장하므로, 한 유닛이 같은 아군에게 이동/공속/피해량 버프를 동시에 걸어도
값이 서로 안 섞이고, 서로 다른 여러 버퍼가 같은 아군을 동시에 버프하면 축별로 곱연산
중첩된다.

`TowerReinforcementAuraEffect`는 대상이 타워라는 점만 다르고 나머지 구조(매 틱 거리 스캔,
`attackRange`를 오라 반경으로 재사용)는 동일 — `TacticalRelayAuraEffect`의 타워 버전이라고
생각하면 된다. 실제 반영은 `TowerDamageMath`가 계산 시점에 조회하므로, 같은 타워가 스킬 타워의
`AuraBuffEffect`(상시 등록) 사거리 안에도 동시에 있으면 두 버프가 곱연산으로 함께 적용된다.

## 4. 예시 조합 레시피

아래는 전부 새 C# 없이 기존 부품만 조합한 예시다. 실제 수치는 밸런싱 대상이니 참고용.

**관통 저격 지원조 (2유닛 세트)**
- 저격수: `PierceAttackEffect`(주공격) — `attackDamage` 높게, `attackRange` 김
- 근처 지휘관: `DamageBuffAuraEffect` + `TowerReinforcementAuraEffect` — 저격수와 인접 타워
  양쪽의 화력을 동시에 끌어올림

**독폭발 유격병 (1유닛)**
- `SplashAttackEffect`(주공격, `splashDamageMultiplier` 낮게 0.3~0.4) 또는
  `PoisonAttackEffect`(주공격) 하나로 지속딜 특화 — 스플래시와 독은 둘 다 "주 공격"이라 동시에
  못 얹으므로, 광역 즉발이 필요하면 Splash, 지속딜이 필요하면 Poison 중 하나를 고른다.

**이동식 야전 정비소 (1유닛, aurora-slow-drone류 서포트 패턴 확장)**
- `attackDamage=0`, `PitCrewRepairAuraEffect` + `TacticalRelayAuraEffect` 동시 장착 — 회복과
  이동/공속 버프를 한 대에서 겸하는 올인원 서포터. 두 오라 모두 "근처 아군"을 각자 독립적으로
  스캔하므로 서로 간섭하지 않는다.

**디버프 전초기지 (aurora-debuff-drone류 확장)**
- `VulnerableAuraEffect` + `SlowAuraEffect`(Unit) 동시 장착 — 같은 적 무리에게 슬로우와 취약을
  동시에 걸어 후방 딜러의 처리 속도를 높임.

## 5. 확장 시 알아둘 내부 구조

새 스탯 축(예: 사거리 버프, 방어력 버프)을 추가하고 싶다면:

- 아군 유닛 버프는 `StatMultiplierSet`(`Assets/Scripts/Runtime/StatMultiplierSet.cs`, 현재
  이동/공속/피해량 3축)에 필드를 추가하고, `AllyUnitInstance`에 `CalculateXxxMultiplier()`를
  하나 더 만들어 소비 지점(이동/공격/피해 계산부)에서 곱해주면 된다.
- 타워를 대상으로 하는 새 버프는 `ITowerAura`(`Effects/Tower/ITowerAura.cs`)에 축을 추가하거나,
  `SimpleTowerAura`(`Effects/Tower/SimpleTowerAura.cs`)처럼 새 `ITowerAura` 구현을 만들고
  `TowerInstance.ApplyTemporaryAura`로 걸면 된다.
- (소스, 효과) 키로 짧은 버프를 저장·자동 만료시키는 저장소가 필요하면
  `RefreshableAuraBag<TSource, TEffect, TValue>`(`Assets/Scripts/Core/RefreshableAuraBag.cs`)를
  재사용한다 — `AllyUnitInstance`의 스탯 배율과 `TowerInstance`의 임시 오라가 이미 이 부품을
  공유한다.
- 새 주 공격(예: 관통+독처럼 판정을 합성한 것)이 필요하면, 먼저 §4처럼 기존 주 공격 하나 +
  오라 조합으로 원하는 결과가 나오는지 확인한다. 정말 새 판정이 필요할 때만 새 클래스를 만들고,
  판정 수학은 가능하면 `Assets/Scripts/Core/`의 정적 유틸로 뽑아 Tower/Unit 양쪽이 재사용할 수
  있게 한다(`PierceAttackMath`/`SplashAttackMath`가 그 선례).

## 6. 실제로 새 유닛을 만드는 절차

1. `Assets/Editor/AllyUnitRecipes/*.json`에 레시피 작성 — `effectPaths`에 위 표의 `.asset`
   경로를 원하는 개수만큼 나열(주 공격 규칙은 §2 준수), `data`에 스탯 입력.
2. 에디터 메뉴 `RCCom/Ally Units/Build All Ally Unit Assets`(`AllyUnitAssetBuilder.cs`) 또는
   `RCCom/Ally Units/Open Ally Unit Studio`(`AllyUnitStudioWindow.cs`)로 `AllyUnitDefinition.asset`
   생성/검증.
3. `AllyUnitCombatVerifier`/`AllyUnitAssetValidator`(같은 `Assets/Editor/` 아래)가 배타성 위반
   (주 공격 중복 등)이나 스탯 이상치를 잡아준다 — 빌드 전에 통과시킨다.
4. 신규 오퍼레이터로 묶어 배포하려면 `ADDRESSABLES_LIVE_DROP.md` §4/§5 절차를 따른다(이 문서의
   조합 자체는 전부 "재빌드 없이 배포 가능" 항목에 해당).

  유닛의 실제 레시피)
