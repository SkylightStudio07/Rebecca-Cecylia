## 초기 프롬프트
개발 착수 전, 코딩 AI(Claude Code)에게 아래 내용을 초기 프롬프트로 전달해 작업 규칙을 계약함.

```
(본인은 클로드의 개인 메모리 기능을 끄고 사용함.)

[넥슨 공지 이메일 내용.txt]
[해당 기획서 노션 링크]

넥슨 게임잼 '재밌넥'에 일차 서류를 합격해서, 과제전형을 7월 6일 15시까지 진행해야 해.

과제전형 관련 공지사항은 이메일에, 그리고 노션에는 일차적으로 기획을 진행한 내용이 작성되어 있어.

나(user}는 게임업체 취직용 유니티 포트폴리오가 이미 몇 개 있고, 유니티를 일반적으로 사용할 수 있어.

현재 기획서에 따라 DAY 1 내용을 개발해야 하며, 개발의 용이를 위해 해당 아키텍쳐를 일반적으로 따르는 것이 좋음.

1. 데이터 컨테이너(비 Monovihaviour 스크립트 - TowerData, EnemyData 등)
2. 데이터 기반 SO(TowerAbility, EnemyAbility 등)
3. 렌더러 프리팹(Attack_Tower_Default.prefab 등)
4. 매니저

* 해당 사항을 자체적인 .md 파일에 기록해두고 개발을 진행할 것.
* 만약 개발을 진행 중 기획이 명확하지 않은 부분이 있으면 개발을 중단하고, {{user}}에게 질문할 것.
* 한꺼번에 전부 수행하려고 하지 말 것. 한 번에 한 모듈(Enemy, Tower 등), 혹은 그보다 작은 단위로 진행.
* 개발 진행중 특기할 사항 및 진행 상황 [노션 개발 진척 페이지]에 작성할 것.
* 타워의 설치는 그리드(TileMap)으로 진행되어야 하며, 적과 플레이어의 움직임은 그리드와 관계가 없어야 함.
* 절차적 생성으로 구현되는 적 웨이브 시스템은 난수 독립성과 재현성을 보장해야 함.
* 바이브 코딩용 컴포넌트를 무리하게 개발하기보다, {{user}}에게 인스펙터에 데이터를 끌어다 놓도록 지시할 것.
* 출력문의 마지막에는 {{user}}이 해당 진척사항과 관련되어 무슨 태스크를 수행해야 하는지 명시할 것.
```

### Day별 AI 활용 상세

**Day 1 (7/3)** — Claude Code(Sonnet 5)가 데이터 컨테이너 → 효과 훅 레이어 → Definition SO → 매니저(Map/Wave/Game) 순으로 4계층 아키텍처를 처음부터 쌓음. 이 시점에는 아트/사운드 없이 플레이스홀더로 코어 루프(적 스폰→이동→공격→보상)만 검증.

**Day 2 (7/4~5)** — Claude Code가 그리드 빌드 시스템, 예산 기반 웨이브 절차적 생성, 카드 15장, HUD를 구현. 이 단계부터 GPT로 UI/스프라이트 디렉팅 병행 시작 — GDD의 아트 레퍼런스 이미지를 기준으로 대화형으로 반복 생성.

**Day 3 (7/5~6)** — 가장 많은 AI 도구가 동시에 투입된 구간:
- Claude Code: 세션 중 모델을 Sonnet 5 → Fable 5로 전환, 타워 18종 확장/시각·청각 피드백/메타 화면(오퍼레이터·튜토리얼·결과화면)/사운드 매니저까지 전 구간 담당.
- Codex(VS Code 확장): 타이틀 씬(타이틀→메인 메뉴 전환 연출, 설정 화면 버튼 로직)을 독립적으로 구현. 이후 Claude Code가 이 코드에 사운드/볼륨/해상도 시스템을 통합하는 과정에서, 서로 다른 세션에서 만들어진 볼륨 처리 로직이 중복·충돌하는 사례를 발견해 정리(상세는 작업물 리포트 "어려웠던 점" 참조).
- GPT: 타이틀 실루엣, HUD 아이콘, 카드/빌드 메뉴 프레임 등 시각 자산 생성 지속.
- ElevenLabs: 타워 공격/플레이어 공격/스킬/버튼 클릭/타워 설치·철거 등 전 효과음을 상황을 서술하는 짧은 프롬프트로 생성.
- BGM 라이선스 리서치: 당초 NCS(NoCopyrightSounds)를 검토했으나, Claude Code가 `ncs.io/usage-policy`를 실시간으로 조회해 "무료 라이선스는 영상/스트리밍 한정이며 게임 배포물 삽입은 별도 상업 라이선스 대상"임을 확인. 평가용 제출물의 라이선스 리스크를 사전 차단하기 위해 게임 사용이 명시적으로 허용된 Pixabay Music으로 교체.

### AI 산출물 통합 시 유의점 (실제 겪은 사례)
여러 AI가 서로 다른 세션에서 독립적으로 코드를 작성하다 보니, 같은 기능(예: 볼륨 설정)이 두 곳에 중복 구현되어 있고 그 중 하나가 실제로는 미완성 상태로 방치된 경우가 있었다. 이런 사례는 복수 AI 협업에서 "새 기능을 붙이기 전에 기존 시스템의 존재 여부를 먼저 확인시키는" 절차가 필요함을 보여준다 — 사람이 최종 통합/검수를 담당해야 하는 이유이기도 하다.
