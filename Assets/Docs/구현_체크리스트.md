# 구현 체크리스트 (Day 1-3) — R&C Company (TVD)

> GDD에서 확정된 시스템을 기반으로 작성한 일자별 구현 체크리스트. **필수**는 반드시 끝내야 하는 항목, **여유시**는 시간 남으면 추가하는 폴리싱/확장 항목. 최종적으로 아래 필수 항목은 전부 완료되었고(체크박스는 최초 작성 시점 초안 상태 그대로 보존), 실제 진행 로그는 이 문서 하단에 이어서 기록했다.

## 아키텍처 재정비 - 2026-07-04
기존 Day 1 결과물(위 진행 현황)은 애드혹 스크립트 구조였음. 이번 세션부터는 재사용/확장성을 위해 아래 4계층 아키텍처로 재구성하며, 코드베이스에는 `Assets/Docs/ARCHITECTURE.md`에 상세 결정 로그를 별도 기록함.

1. 데이터 컨테이너 (비 MonoBehaviour, 순수 C# — TowerData / EnemyData / PlayerData)
2. 데이터 기반 SO (TowerAbility / EnemyAbility 등, 다음 단계)
3. 렌더러 프리팹 (다음 단계)
4. 매니저 (다음 단계)

### 진행: 1단계 — 데이터 컨테이너 (완료)
- `EnemyData.cs`: `EnemyKind`(Normal/Rusher/Tanker/Boss) + 체력/속도/접촉피해/웨이브코스트/등장웨이브/보상 필드. 3종은 로직이 아닌 수치 차이라 단일 클래스로 설계.
- `TowerData.cs`: 공통 베이스 + `AttackTowerData`(데미지/사거리/공속) / `SkillTowerData`(오라 사거리/버프 배율) / `PowerTowerData`(글로벌 버프/누적치) 3개 파생 클래스. GDD가 3분류를 확정했고 타입별 필드가 다르므로 상속으로 분리.
- `PlayerData.cs`: 체력/이동속도 + 기본 공격(데미지/사거리/공속/투사체속도) + 스킬(쿨다운/범위/피해) 필드.

## 매니저 아키텍처 정정 - 2026-07-04
{{user}} 확인: "그리드는 MapManager가 맞고, Tower/Enemy 매니저는 굳이 필요한가 싶다" → GDD 기술 노트에 Project Vertex 실제 코드 분석 기반 원칙이 추가됨: **매니저는 "게임 흐름 단계"당 1개(GameManager/MapManager/WaveManager/CardManager 4개뿐), "오브젝트 타입"별 매니저(TowerManager/EnemyManager)는 만들지 않는다.**

### 이전 설계 정정

### 코드 반영
- `TowerInstance` → `MonoBehaviour`로 전환. 자기 `Awake()`/`Update()`/`OnTriggerEnter2D`/`OnTriggerExit2D`에서 직접 효과 훅 호출 (별도 TowerManager 없음). 아군/적 감지 둘 다 Collider2D 트리거로 통일.
- `EnemyInstance`는 순수 C# 유지 + `Spawn()`/`Tick()`/`DealContactDamageTo()`/`TakeDamage()`가 스스로 효과 훅 구동, `Damaged`/`Died` 이벤트 추가.
- `EnemyView`(신규, MonoBehaviour) — 로직 없이 위치 반영 + 사망 시 자기 파괴만 담당.
