## 기획 의도 (Design Rationale)
모든 결정은 다음 제약 조건을 기준으로 내렸다: **1인 개발, 3일(7/3~7/6) 제작 기간, Unity 상급 숙련도, AI-Native 게임잼 평가 기준(AI 활용도 + 종합적 게임제작 역량)**.

**장르: 하이브리드(직접 조작 + 타워)**
순수 타워 디펜스는 배치/업그레이드 UI 비중이 높고, 재미가 거의 전적으로 밸런싱에 종속되어 3일 안에 완성도를 내기 어렵다고 판단. 하이브리드는 플레이어 조작이 즉각적인 재미를 주고, 타워는 적은 종류로도 전략적 깊이를 줌 → 구현량을 양쪽으로 분산시켜 리스크를 낮춤.

**성장: 랜덤 업그레이드 카드 (뱀서 스타일 3택)**
정교한 타워 트리를 처음부터 설계하는 대신, 카드 풀을 넉넉하게 만들어두면 조합이 자연스럽게 다양해지는 구조로 밸런싱 부담을 줄임. 동시에 매 판 다른 조합이 나오는 리플레이성을 확보해 3분 시연 영상에서도 "성장하는 느낌"을 보여줄 수 있음.

**절차적 생성: 웨이브만 적용, 맵은 미도입**
맵 절차적 생성은 경로탐색·디버깅 비용이 크고, 매판 타워를 다시 배치해야 하는 피로도가 효과 대비 크다고 판단해 제외. 대신 구현 비용이 낮고 효과가 확실한 웨이브 구성 절차적 생성에 리소스를 집중해, AI를 활용한 밸런싱 설계를 보여줄 포인트로 삼음.

**맵 구조: 단일 경로**
오픈 필드는 적 경로탐색(NavMesh/A*)과 플레이어 방어 동선 설계가 복잡해져 범위를 초과한다고 판단. 단일 경로는 웨이포인트만으로 구현 가능하고, 단계별로 경로 모양만 바꾸어도 충분히 다른 느낌을 줄 수 있음.

**타워 구조: 공격/스킬/파워 3분류**
직접 딜러(공격), 범위 버프(스킬), 글로벌 버프(파워)로 역할을 분리해 서로 다른 배치 전략(클러스터링, 타이밍)이 자연스럽게 발생하도록 설계. 적은 타입 수로도 조합의 폭이 넓어지는 구조를 노림.

**타워 설치 슬롯 제한**
무제한 타워 도배를 막고, 카드로 슬롯을 확장하는 것 자체를 빌드 전략으로 만들기 위해 도입. 특히 스킬 타워는 버프형이라 수가 많아지면 밸런스가 쉽게 무너져 기본값을 낮게 잡음.

**플레이어 체력**
만약 플레이어가 무피해하다면 "이동 가능한 포탑"이 되어버려 핵심 재미(직접 조작의 액션감)가 생기지 않는다고 판단해 도입. 다만 적이 플레이어를 별도로 추적/타겟팅하는 어그로 시스템은 구현 비용만 늘리므로 제외. 대신 적은 기존처럼 경로만 따라 가다가 플레이어와 거리가 가까워지면 접촉 데미지만 입히는 수동적 방식으로 최소 비용으로 위험 요소를 확보.

**적 구조: 베이스 3종 + 수식어**
적 종류를 늘릴수록 그래픽·애니메이션 작업량과 웨이브 생성 규칙의 분기가 함께 늘어나는 문제가 있음. 베이스 3종(체력/속도 트레이드오프) + 수치 배율 기반 수식어로 체감 다양성을 늘리면 그래픽 작업은 최소화하면서도 웨이브마다 다른 게임처럼 느껴지게 함. 툴백 라인(스프라이트만 교체)도 동일한 이유로 미리 준비.

**웨이브 난이도 생성: 예산(Budget) 방식**
수동 밸런싱 대신 숫자 몇 개(기본예산, 성장계수, 적 코스트)만 조정하면 난이도 곡선이 통째로 따라오는 구조를 택함. 구현과 밸런싱 양쪽의 시간 비용을 다 줄이는 선택.

**카드 풀 비중 (타워/거점 관련 73%)**
랜덤 성장을 도입하더라도 게임이 "디펜스"라는 정체성을 잃지 않도록 타워/거점 관련 카드 비중을 의도적으로 높게 설계 (플레이어 강화만 계속 나오면 사실상 뱀서라이크가 되어버림).

## 게임 루프
1. 웨이브 시작 → 적 스폰
2. 플레이어 이동/공격으로 적 처치 + 경험치/자원 획득
3. 레벨업 시 카드 3장 중 1개 선택 (랜덤 업그레이드 — 플레이어 강화 / 타워 강화 / 신규 타워 해금 등)
4. 처치 보상(골드 등)으로 타워 설치/수동 업그레이드
5. 웨이브 클리어 → 다음 웨이브 대기(빌드 페이즈) — ✅ 10초 고정, 카운트다운 UI로 표시 (첫 웨이브 시작 전에도 동일하게 적용, 개발 중 확정 2026.07.05)
6. 반복, 난이도 상승

*(세부 수치·조건은 추후 논의)*

- 이동
- 원거리 기본 공격
- 스킬 (사용처량/쿨다운 기반, 세부는 추후 논의)
- 다이: ✅ 보유함. 적은 플레이어를 추적하지 않고 경로만 따라 이동하다가, 근접 거리 안에 들어오면 접촉 데미지를 입힘 (거리 판정 1줄로 처리, 별도 어그로/타겟팅 AI 없음)
  - 데미지 방식: ✅ 스치는 순간 1회성 데미지 (지속 데미지 X). 동일 적에게 연속 피격 방지를 위해 피격 후 짧은 무적/쿨다운 필요
- 패배 조건: 거점 체력 0 또는 플레이어 체력 0

### 타워
- 종류: 3종 ✅ 확정 — 공격 / 스킬 / 파워
  - **공격 타워**: 직접 딜러. 사거리 내 적을 공격. 데미지/사거리/공속으로 강화
  - **스킬 타워**: 범위 버프. 자기 사거리 내에 있는 공격 타워를 상시 강화(공격력/공속 등). 사거리 이탈 시 버프 상실 → 배치 타이밍이 전략 핵심
  - **파워 타워**: 글로벌 버프. 건설 즉시부터 전체 상시 버프 적용 (예: 전체 공격력 +2). 강화 시 수치 누적 상승(+0.5씩). 사거리 개념 없음, 조기 건설이 유리
- 설치 방식: 그리드 스냅 ✅ 확정 (경로 주변에 설치 슬롯 배치)
- 타워 설치 슬롯 제한 (카드로 확장, 아래 참조)
  - 공격 타워 기본 3 / 스킬 타워 기본 1 / 파워 타워 기본 2
- 업그레이드 여부: *(미정)*

### 적
- 종류: 베이스 3종 ✅ 확정
  - **일반형**: 표준 체력/속도
  - **돌진형**: 체력↓ 속도↑ (반응속도 테스트)
  - **탱커형**: 체력↑ 속도↓ (화력집중 테스트)

### 웨이브 절차적 생성 (채택)
- 맵/타일은 고정, 대신 웨이브마다 적 구성을 규칙 기반으로 절차적 생성
- 웨이브 번호에 비례해 난이도 예산을 배분 → 적 종류/수량/스폰 간격을 규칙으로 결정
- 맵 절차적 생성은 미도입 (피로도 대비 효과 미흡 판단, 매번 타워 재배치해야 하는 부담 회피)

#### 웨이브 난이도 생성 규칙 (난이도 예산 방식, 초안)

**1. 웨이브별 예산**
```
예산(n) = 기본예산 + 성장계수 × n
예: 예산(n) = 10 + 2n  → 웨이브1: 12, 웨이브5: 20, 웨이브10: 30
```

**2. 적 코스트 & 등장 시점**

| 타입 | 코스트 | 등장 시작 웨이브 |
|---|---|---|
| 일반형 | 1 | 1 |
| 돌진형 | 1.5 | 3 |
| 탱커형 | 2.5 | 5 |

**3. 소환 로직 (의사코드)**
```
남은예산 = 예산(n)
등장가능풀 = 웨이브번호에 따라 필터링된 적 종류
while 남은예산 > 0:
    적종류 = 등장가능풀에서 가중치 랜덤 선택
    수식어 = (n >= 5) 이면 확률적으로 정예/무리 부여
    소환큐에 추가
    남은예산 -= 적종류.코스트 × 수식어.코스트배율
```

**4. 수식어 확률**
```
정예 확률 = min(0.4, 0.05 × (n - 4))   // 5웨이브부터 증가, 최대 40%
무리 확률 = min(0.3, 0.03 × (n - 4))
```

**5. 스폰 간격**
```
간격(n) = max(0.5초, 2.0초 - 0.05 × n)
```

**6. 보스 웨이브**
```
n % 5 == 0 → 보스 웨이브 (예산 절반 + 보스 단독 등장)
```

**7. 웨이브 간 빌드 페이즈 (대기시간)** ✅ 확정 (2026.07.05, 개발 중 결정)
```
빌드페이즈시간 = 10초 (고정값)
```
- 웨이브 클리어 직후 및 첫 웨이브 시작 전에도 동일하게 10초 대기 적용
- 대기 중에만 HUD에 남은 시간 카운트다운 표시 — 이 구간이 실질적인 "타워 설치/재배치 타이밍 창"이므로 플레이어가 남은 시간을 인지하고 결정할 수 있도록 함

## 기술 노트 (Technical Notes)

> 이전 개인 프로젝트(Project Vertex, 슬레이 더 스파이어 모작)의 `CardEffect`/`IPassiveLogic` 자산을 타워 특수능력에 재활용하기 위해 Claude와 논의한 구조. 실제 구현 전 코드리뷰 기준으로 삼을 것.

### 왜 기존 `CardEffect`를 그대로 못 쓰는가
원본 프로젝트는 "턴에 한 번 실행되고 끝"나 `Execute(context)` 단일 진입점으로 충분함. 하지만 타워는 시점이 여러 개로 갈림:
- **공격 타워**: 공격 주기마다 반복 실행 (Tick)
- **스킬 타워**: 적이 아니라 **아군 타워**가 사거리에 들어오고/나가는 것을 감지해야 함 (Enter/Exit)
- **파워 타워**: 건설 즉시 1회 실행, 이후 트리거 없음 (OnBuild)

기존 `CardEffect`는 업그레이드 카드(1회성 실행)에 그대로 쓰고, 타워 특수능력은 별도 계약으로 분리한다.

### 타워 훅 계약: 인터페이스 + 편의용 추상 클래스 병행
순수 인터페이스만 쓰면(`IPassiveLogic` 스타일) 안 쓰는 훅도 매번 빈 구현해야 해서 보일러플레이트가 늘어남. 타워 특수능력은 5~8종 내외로 적으니 "계약은 인터페이스, 편의는 추상 클래스" 둘 다 가져간다.

```csharp
public interface ITowerEffect
{
    void OnBuild(TowerContext ctx);
    void OnTick(TowerContext ctx);
    void OnAllyEnterRange(TowerContext ctx, TowerInstance ally);
    void OnAllyExitRange(TowerContext ctx, TowerInstance ally);
}

// 다른 시스템(TowerManager, 세이브 등)은 이 클래스가 아니라
// 위 인터페이스에만 의존하게 해서 독립성을 유지한다.
public abstract class TowerEffectBase : ScriptableObject, ITowerEffect
{
    public virtual void OnBuild(TowerContext ctx) {}
    public virtual void OnTick(TowerContext ctx) {}
    public virtual void OnAllyEnterRange(TowerContext ctx, TowerInstance ally) {}
    public virtual void OnAllyExitRange(TowerContext ctx, TowerInstance ally) {}
}
```

실제 효과 작성자는 `TowerEffectBase`를 상속받아 필요한 훅만 오버라이드한다. 예: `DamageEffect`는 `OnTick`만, `AuraBuffEffect`는 `OnAllyEnterRange`/`OnAllyExitRange`만 구현.

### 스킬 타워 버프: 직접 가감 대신 파이프라인 조회 방식
처음에 검토했던 "사거리 진입/이탈 시 공격력 수치 직접 가감(+15%/-15%)" 방식은 버프 중복/이탈 처리 누락/부동소수점 누적 버그에 취약해서 폐기. 대신 `IPassiveLogic`의 `ModifyOutgoingDamage` 패턴을 차용해, 공격 타워가 자기에게 걸린 버프 "목록"만 들고 있다가 데미지 계산 순간에 조회하는 방식으로 대체한다. 스탯 자체는 절대 건드리지 않음.

```csharp
public interface ITowerAura
{
    float ModifyOutgoingDamage(float baseDamage);
}

// 공격 타워 쪽
List<ITowerAura> activeAuras = new();

float CalculateDamage()
{
    float dmg = baseDamage;
    foreach (var aura in activeAuras)
        dmg = aura.ModifyOutgoingDamage(dmg);
    return dmg;
}
```

스킬 타워는 `OnAllyEnterRange`에서 `activeAuras.Add(this)`, `OnAllyExitRange`에서 `Remove(this)`만 하면 된다. 사거리 이탈 시 버프가 자동으로 사라지고, 여러 버프가 겹쳐도 안전하게 누적된다.

### 상태이상(StatusType)은 그대로 재사용
`Weak/Vulnerable/Poison/Strength/Dexterity` 개념을 타워 특수능력에도 거의 그대로 쓴다.
- 빙결 오라 타워(카드14) → `Slow` 상태 하나만 추가
- 재생의 축(카드15) → `Regen` 상태를 거점에 부여
- 향후 "독 타워" 생기면 기존 `Poison` 그대로 재사용 가능

### 요약
- **계약**: `ITowerEffect` 인터페이스 (독립성 보장)
- **편의**: `TowerEffectBase` 추상 클래스로 기본 빈 구현 제공
- **스킬 타워 버프**: 직접 가감 대신 `ITowerAura` 조회 리스트 방식
- `CardContext` → `TowerContext`로 이름만 바꾸고 `TowerInstance self`, `float range` 등 필드 추가

### 매니저 아키텍처 (Project Vertex 코드 분석 기반)
> 이전 프로젝트 Vertex(SkylightStudio07/Project-Vertex)의 실제 스크립트 구조를 분석해 도출한 원칙. Vertex에는 GameManager/BattleManager/MapManager/DeckManager/ItemInventoryManager/CooperationManager 등 여러 매니저가 있지만, **모두 "게임 흐름 단계"별로 1개씩이지, "오브젝트 타입"별 매니저(EnemyManager, CardManager 등)는 하나도 없음**. 적/카드 개체 로직은 전부 개체 자신이 들고 있음.

**근거: `EnemyInstance.cs`**
```csharp
// 해당 파일 주석 그대로 인용:
// "퍼포먼스 문제 때문에 일부러 MonoBehaviour 상속 안 했으니까 수정 누누"
public class EnemyInstance : ICombatant  // 순수 C# 클래스, MonoBehaviour 아님
{
    // HP/블록/패시브를 스스로 보유, OnDamaged/OnDied 이벤트로 외부에 알림
}
// EnemyView(MonoBehaviour)는 이 이벤트를 구독해 화면만 갱신. BattleManager는 List<EnemyInstance>를
// 들고 턴 순서만 조율할 뿐, 개별 로직에는 개입 안 함 → EnemyManager 자체가 존재하지 않음.
```

`DamageCalculator`도 싱글톤이 아니라 `static class` 파이프라인 함수로만 존재함. 굳이 매니저일 필요 없는 건 매니저로 안 만드는 원칙이 일관됨.

**TVD 적용**
TVD는 실시간 웨이브 디펜스라 Vertex(턴제, 동시 적 수 5인 안팎)보다 화면상 적 개체 수가 훨씬 많을 수 있어서, MonoBehaviour 개체별 Update() 오버헤드가 더 치명적임. 그래서 이 패턴이 Vertex보다 오히려 TVD에 더 가치가 큼.

```csharp
// 순수 C# — Vertex의 EnemyInstance와 동일한 이유
public class EnemyInstance
{
    public float HP { get; private set; }
    public Vector2 Position { get; private set; }
    public event Action OnDied;

    public void Tick(float dt) { /* 이동 + 상태 갱신 */ }
    public void TakeDamage(float amount) { /* ... */ }
}

// WaveManager가 자기 Update()에서 리스트를 직접 순회 (별도 EnemyManager 없이)
void Update()
{
    foreach (var e in aliveEnemies)
        e.Tick(Time.deltaTime);
}

// EnemyView(MonoBehaviour, 스프라이트 붙은 실제 오브젝트)는
// 매 프레임 자기 EnemyInstance의 Position만 읽어 transform.position에 반영
```

**타워는 반대**: 설치 슬롯 제한(최대 6~8개) 때문에 개체 수가 적어서, 억지로 순수 C#화할 필요 없음. 일반 MonoBehaviour + Collider Trigger로 그대로 두면 됨.

**최종 매니저/아키텍처 구성 표**

| 구분 | Vertex 패턴 | TVD 적용 |
|---|---|---|
| 매니저 | 게임 흐름 단계별 (Game/Battle/Map...) | GameManager / MapManager / WaveManager / CardManager (4개) |
| 다수·고빈도 개체 | EnemyInstance = 순수 C#, View가 구독 | 적 = 순수 C# + Tick(), EnemyView가 Position 반영 (WaveManager가 순회) |
| 소수 개체 | — | 타워 = 일반 MonoBehaviour (개수 적어서 오버헤드 무의미) |
| 연산 파이프라인 | DamageCalculator = static class | 데미지 계산도 static 함수로 (매니저 아님) |

**원칙**: 매니저는 "게임 흐름 단계"당 1개만 존재하고, "오브젝트 타입"당 매니저는 만들지 않는다. 개별 오브젝트(적/타워/카드)는 스스로 상태를 들고 이벤트로 외부에 알리며, 매니저는 리스트를 순회하거나 흐름만 조율한다.

> 실제 구현 단계에서는 여기에 5번째 예외로 `SoundManager`가 추가되었다(오디오 재생은 "게임 흐름 단계"로 분류되지 않는 횡단 관심사 서비스로 판단). 상세 근거는 `Assets/Docs/ARCHITECTURE.md`의 "사운드 매니저" 섹션 참조.

## 효과 중첩 규칙 (2026-07-06, 개발 중 정리)
여러 타워/카드 효과가 같은 대상에 동시에 걸릴 때 곱연산/합연산으로 폭주하지 않도록 아래 원칙으로 구분해서 구현함.

**적 상태이상(감속/취약/맹독) — 중첩 안 됨, 덮어쓰기만**
빙결 오라·취약 오라·맹독 타워가 같은 적에게 동시에 걸려도 배율이 곱해지지 않는다. 매 틱 "마지막으로 적용된 값"으로 갱신(지속시간만 리프레시)되는 구조라, 타워를 아무리 겹쳐 지어도 속도/피해 배율이 0으로 수렴하거나 폭주하지 않음 — 여러 대를 지어도 그 중 한 대의 설정값 이상으로 세지지 않는다.

**타워 버프(스킬 타워 오라, 파워 타워 글로벌 버프) — 의도적으로 중첩됨**
- 스킬 타워의 공격력/공속 버프는 사거리가 겹치는 스킬 타워 개수만큼 **곱연산으로 누적**된다 (예: +20% 버프 스킬 타워 3개 겹치면 1.2³ ≈ 1.73배). 배치 전략의 핵심이라 의도된 동작.
- 파워 타워 글로벌 버프는 지어진 개수만큼 **합연산으로 누적**된다. 역시 의도된 동작.
- 업그레이드 카드로 얻는 영구 스탯 배율도 같은 카드를 여러 번 뽑으면 곱연산으로 누적(로그라이크 성장 의도). 단, "스킬 타워 버프 강화" 카드는 배율 자체가 아니라 "보너스 부분"만 강화하도록 설계해 극단적 폭주를 방지함 (1.2배 → 1.25배지 1.2×1.25배가 아님).

**결론**: 어느 조합으로 타워를 도배해도 나눗셈이 0이 되거나 NaN이 나는 경우는 없음 — 스킬 타워 공속 버프를 과도하게 겹치면 체감 난이도가 비정상적으로 쉬워질 수 있는 정도의 밸런스 이슈만 존재. 플레이테스트 시 다수의 스킬 타워를 겹쳐 짓는 극단적 빌드도 한번 확인해볼 것.
